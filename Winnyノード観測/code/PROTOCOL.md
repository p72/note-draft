# Winny 2 (b7.1) プロトコル仕様 — 観測専用クローラ実装のための最小仕様

- 対象ソース: `~/workspace/winny-research/src/71/`(Winny 2.0 b7.1 のリバースエンジニアリング再構成、C++Builder)
- 目的: ノード列挙とキー情報(ファイル名・サイズ・ハッシュ)の**受信専用**観測クライアントを実装するための仕様整理
- 表記: 各項目に根拠(ファイル名 / 関数名 / 行番号の目安)を付す。行番号は CP932→UTF-8 変換後も元ファイルと同一。
- = ソースから直接読み取れたこと
- = ソースの断片からの推論(未検証)
- = 第10節の一覧に集約
- エンディアン: 特記なき限りすべて **リトルエンディアン**、文字列は原則 Shift_JIS / バイト列として扱う。

> 注意: このソース自体が再構成(reconstruction)であり、実バイナリとの完全一致は保証されない(リポジトリ側もその旨を明記)。実トラフィックでの検証が別途必要(第10節)。

## 1. 暗号プリミティブ

### 1.1 RC4
`CRC4` クラスは教科書どおりの RC4 ストリーム暗号。
- `CRC4::setupkey(const char*)`(`CRC4.cpp` L27): 標準 KSA。鍵は **NUL 終端文字列**として扱われ、S-box 生成時に繰り返し使われる。
- `CRC4::crypter(char*, int)`(`CRC4.cpp` L74): PRGA 鍵ストリームとの XOR(`mf_CRC4_0000`, L62)。
- **鍵キャッシュ**: `setupkey` は前回と同じ鍵文字列なら保存済み S-box を再利用し、インデックスだけリセットする(同ファイル)。
- 接続ごとの送受信 RC4 状態は `CHost` 内に埋め込みで保持される(`CHost.h`: 送信用/受信用の S-box とインデックス)。
- 全体共有の静的インスタンス `CKey::g_CRC4`(`CKey.h` L132)もあり、文字列コーデック類はこちらを使う。

鍵が「文字列」であるため、**鍵バイト列に 0x00 が含まれると、そこで鍵が打ち切られる**(`strlen` 意味論)。後述するシード鍵でこの性質がそのまま仕様になる。

### 1.2 固定文字列鍵の一覧(ソース内の全 `setupkey` リテラル)
| 鍵文字列 | 用途 | ワイヤに関係 |
|---|---|---|
| `"98789asj"` | ハロー(タイプ0)ペイロードの二重暗号化 | **する** |
| `"opiewf6ascxlv"` | 初期ノード文字列のコーデック(先頭1バイトはチェックサムに置換される) | **する**(ノード文字列内) |
| `"header"` / `"adsfu6"` | ローカルキャッシュファイルのヘッダ復号(`CKey::mf_CKey_0100`, `CKey.cpp` L487) | しない |
| 1バイト鍵(=ファイル名バイト和の下位1バイト) | キー情報内のファイル名難読化(§6.2) | **する** |

**トランスポート自体を暗号化する固定秘密鍵は存在しない。** 接続の暗号鍵は接続開始時に平文で交換される 4 バイトシードから導出される(§2)。固定鍵 `"98789asj"` はハローの中身を包むだけのものである。

## 2. 接続開始シーケンス

接続は TCP。発信側は `CMainControl::mf_CMainControl_0260`(`CMainControl.cpp` L826、非ブロッキング connect + WSAAsyncSelect)、着信側は `mf_CMainControl_0290`(L1020、accept)。対象アドレスはホストエントリの `ipaddr3`(実アドレス):ポート `port1`(BBS テスト接続時は `port2`)。

### 2.1 シード交換(暗号の前段)

1. 各接続の初期化(`CHost::mf_CHost_0010`, `CHost.cpp` L67)で、送信用シード `m_cryptseed_send[4]` に `rand()%256` の **4 バイト乱数**を生成する(`CHost.h` オフセット108)。受信用シード `m_cryptseed_recv[4]`(オフセット116)は 0 クリア。
2. **最初の暗号化送信**(`CHost::mf_CHost_0160`, `CHost.cpp` L379)時、ワイヤの先頭に平文で次を前置する:
- ランダム 2 バイト(平文、内容は無意味)
- 自分の `m_cryptseed_send` 4 バイト(平文)

続いて送信 RC4 を「シードを C 文字列とみなした鍵」で初期化し、以降のデータを暗号化する。シード直後のバイトは 0 に保たれるため(`CHost.h` オフセット112)、**実効鍵 = シード先頭から最初の 0x00 の直前まで(最大4バイト)**。受信側も同じ規則で鍵を作るため、シード中に 0x00 があっても両側で一致する。
3. 受信側(`CMainControl::mf_CMainControl_0360`, `CMainControl.cpp` L1312): 受信鍵が未設定なら、最初のチャンクは 6 バイト以上必要。**バイト[2..6) を相手のシードとして `m_cryptseed_recv` に取り込み**、受信 RC4 を初期化する(`CHost::mf_CHost_0060`, `CHost.cpp` L183)。先頭 2 バイトは読み捨て、6 バイト目以降が復号対象のストリームになる。

### 2.2 ハンドシェイク(両方向・対称)
接続確立直後、**発信側・着信側の双方**が `CMainControl::mf_CMainControl_0670`(`CMainControl.cpp` L3698)を実行し、同じ列を送信する(発信側: 接続完了時 `mf_CMainControl_0270` L917 から、着信側: accept 処理 `mf_CMainControl_0290` の末尾から呼ばれる)。順序:

| # | 内容 | 形式 |
|---|---|---|
| 1 | マーカー | 1バイトパケット `0x61` ('a')。受信ディスパッチでは 0x60–0x63 は無視される(実質ノーオペレーション) |
| 2 | **ハロー(タイプ0)** | 21バイトパケット。下記 §2.3 |
| 3 | **送信ストリームの再鍵** | ハロー送信直後、自分の送信 RC4 を新鍵で初期化し直す(§2.4) |
| 4 | 回線速度(タイプ1) | パケット `[0]=1` + `float32` 自分の回線速度 |
| 5 | フラグ(タイプ2) | パケット `[0]=2` + 4バイト: [0]=リンク種別(0=検索 / 1=転送 / 2=BBS)、[1]=ポート0フラグ(外部から着信を受けない設定か)、[2]=フラグ(意味未確定)、[3]=BBSノードフラグ |
| 6 | 自ノード情報(タイプ3) | §5.1 |

### 2.3 ハロー(タイプ0)の構造と検証
構築は `mf_CMainControl_0670`、検証は受信ディスパッチ `mf_CMainControl_0780`(`CMainControl.cpp` L4033)のタイプ0分岐。
- パケット: `[0]=0x00` の後に 20 バイトペイロード:
- `[+0..4)` int32 バージョン番号。b7.1 は **12710**(b7.0 は 12700、b6.6 は 12660。§9)
- `[+4..20)` 文字列 `"Winny Ver2.0b1 "` を `sprintf` で書き込んだ 16 バイト(末尾は空白埋め)
- この 20 バイトは、ストリーム暗号化に加えて **固定鍵 `"98789asj"` の RC4 で二重に暗号化**される。
- 受信側の受け入れ条件: 固定鍵で復号後、バージョン int32 が **[12660, 12900) ∪ [20000, 21000)** の範囲内 **かつ** `memcmp(payload+4, "Winny Ver2.0", 12)==0`。満たさなければ切断。
- 相手バージョンが自バージョン(12710)より大きい場合 `mf_CMainControl_0770` が呼ばれる(処理内容は未精読 →)。

### 2.4 ハロー後の再鍵
ハロー受信を正しく検証できた時点で、受信側は受信ストリームを再鍵する。送信側もハロー送信直後に自分の送信ストリームを再鍵する。再鍵の鍵文字列は 4 バイト:
```
key[0] = seed[0]
key[1] = seed[1] ^ 0x39 ('9')
key[2] = seed[2] ^ 0x39
key[3] = seed[3] ^ 0x39
```
ここで `seed` は**その方向の送信側のシード**(受信側から見れば `m_cryptseed_recv`、送信側から見れば `m_cryptseed_send`)。設定は `CHost::mf_CHost_0030`(`CHost.cpp` L132。受信側は対応する受信側設定関数)で行われ、**RC4 状態は新規に初期化される**(ストリームはここから数え直し)。やはり C 文字列意味論のため、途中に 0x00 があれば実効鍵は短くなる。

受信だけでも、(a) 最初の6バイトから相手シードを取り込む、(b) ハローを検証する、(c) ハローを境に受信 RC4 を再鍵する、の3点を正確に実装しないと、その後のフレームは一切復号できない。

## 3. パケットフレーミング


- 1フレーム = **int32 LE のペイロード長(長さフィールド自体の4バイトを含まない)** + ペイロード。
- 長さフィールドも含め、フレーム全体が §2 の連続 RC4 ストリームで暗号化される(送信: `CMainControl::mf_CMainControl_0370` L1391 が長さを前置して `CHost::mf_CHost_0160` へ、受信: `CHost::mf_CHost_0120` L301 が先頭4バイトを試行復号してフレーム完成を判定、`mf_CHost_0150` L355 が切り出す)。
- ペイロード長が負、または呼び出し側上限以上、または異常値の場合、その接続は切断される(`mf_CHost_0150` / `mf_CHost_0190`)。
- コマンド種別 = **ペイロード先頭1バイト**(タイプ)。ディスパッチ `mf_CMainControl_0780`(L4033)は1回に最大5フレーム処理し、`struct_wk_0780` 経由で `data = payload+1` を各ハンドラに渡す。
- 未知のタイプは原則として切断。例外: 0x60–0x63 は無視。

## 4. ノード情報の交換

### 4.1 自ノード情報(タイプ3)
送信構築・受信処理とも `mf_CMainControl_0670` / `0780`(タイプ3分岐)。データ部:
| オフセット | 内容 |
|---|---|
| 0..4 | 自分のグローバル IP(自ホストエントリの `ipaddr3`、= 自分が信じる自分のアドレス) |
| 4..8 | int32 自分の受付ポート |
| 8 | DDNS 名の長さ(バイト) |
| 9,10,11 | クラスタワード 0,1,2 の各長さ(各 ≤100) |
| 12.. | DDNS 名、続いてクラスタワード 0,1,2 を連結 |

受信側の処理:
- 申告 IP/ポートを相手エントリの `ipaddr1`/`port1` に記録。ソケットで観測した実アドレス `ipaddr3` と異なれば **NAT フラグ**を立てる。
- DDNS 名とクラスタワードをエントリに保存(BBS ノードはクラスタワード空として扱う)。
- 続いて `mf_CMainControl_0790`(L~4330)が、(a) 回線速度・ポート・クラスタワードが自分と完全一致する相手を自己接続として切断・無効化、(b) 回線速度比による上り/下り方向の決定、を行う(詳細条件は一部未精読 →)。
- ポート0(着信不可)の相手については、転送リンク用に相手への接続し直しが発生しうる。

### 4.2 ノード紹介(タイプ4)
1パケット = 1ノード。データ部:
| オフセット | 内容 |
|---|---|
| 0..4 | 紹介されるノードの IP(そのノードの `ipaddr3`、すなわち観測済みグローバルアドレス) |
| 4..8 | int32 ポート(`port1`) |
| 8..12 | int32 BBSポート(`port2`、なければ 0) |
| 12 | BBS ノードフラグ(0/1) |
| 13..17 | int32 回線速度 |
| 17,18,19 | クラスタワード 0,1,2 の各長さ |
| 20.. | クラスタワード連結 |

- 受信: `mf_CMainControl_1010`(L6169)が検証(ポート 1–32767、BBSポート 0–32767)してノードバッファに登録。自分自身は除外。
- 送信: `mf_CMainControl_1000`(L6103)が、既知の有効ノードをソート順に **最大31件**まで、接続相手へタイプ4で連続送信する(リンク確立時のノード交換ワークとして実行される)。

### 4.3 ノードバッファ

- 接続・既知ノードは `CHost` 配列(最大 **600** エントリ、インデックス 0 = 自分)に保持される(`CHost.h`、`mf_CMainControl_0200` L650 で自エントリ初期化)。
- 検索・登録は `mf_CMainControl_0560`(L3294、(IP, ポート)で find-or-allocate)。
- `CHost` エントリはアドレスを3組保持する: `ipaddr1/port1`(相手の自己申告)、`ipaddr3`(ソケット観測アドレス)、`ipaddr2/port3`(タイプ23による代替アドレス)、および `port2`(BBSポート)。

### 4.4 Noderef.txt(初期ノードファイル)

- 起動時に `Noderef.txt` と `BbsNoderef.txt` を読み込む(`mf_CMainControl_0190`、`CMainControl.cpp` L635–640)。
- 読み込み `mf_CMainControl_1210`(L7580): **最大100行**。各行:
- `@` で始まる行 → §8 のコーデックで復号(テンプレート `"opiewf6ascxlv"`)。復号結果も `@` で始まる(=検証失敗)行は捨てる。
- 平文は **`ホスト名:ポート`** 形式(`:` で分割、ポートは10進)。ホスト名はドット10進 IP でも DDNS 名でもよい。
- 登録されたエントリは名前解決(`CHost::mf_CHost_0200`、非同期 DNS。ドット10進も解決できる)され、ダウン接続候補としてマークされる。
- 書き出し `mf_CMainControl_1220`(L7643): 既知の有効ノード最大約100件を `IP:ポート` または `DDNS名:ポート` で上書き保存。引数により各行を `@` 暗号化形式にもできる。
- 追記 `mf_CMainControl_1230`(L7701): 1行追加して再読み込みする。

### 5.2 ファイル名の難読化(`CKey::mf_CKey_0280`, `CKey.cpp` L1163)
キー内のファイル名フィールドは **2バイトヘッダ + 本体** の形で保持され、本体は RC4 で難読化される:
- 平文状態(ヘッダ2バイト = 0): チェックサム = 本体バイト列の合計(uint16)。RC4 鍵 = **その合計の下位1バイトだけからなる1文字の鍵文字列**。本体を暗号化し、ヘッダにチェックサム(uint16 LE)を書く。
- 暗号状態(ヘッダ ≠ 0): 鍵 = ヘッダ第1バイト(= チェックサム下位バイト)の1文字鍵で本体を復号し、バイト合計が保存チェックサムと一致するか検証する。不一致ならそのファイル名は `"@"` として無効化される。
- ワイヤ上(§5.3 の CKeyHeader)でもこの「長さ+2バイト」形式のまま運ばれる。観測側は受信したファイル名をこの手順で復号できる。

### 5.3 キー情報の伝播(クエリへの便乗)
**キー情報専用のプッシュコマンドは存在しない。** キーは検索/拡散クエリ(タイプ13)に `CKeyHeader` として同梱されてネットワークを巡回し、各ノードが自分のキーバッファに取り込む。処理の中心は `CMainControl::mf_CMainControl_1130`(`CMainControl.cpp` L6673):

1. 受信したクエリに含まれる全 CKeyHeader を検証して自分のキーバッファ `m_KeyBuffer_`(ハッシュをキーとする multimap)に登録する(`mf_CMainControl_0600` 経由で `insert`、L3544)。主な検証: ハッシュ ≠ 0、参照カウント < 100000、ファイル名の妥当性、自分のアドレスでないこと、BBS 用のサイズ/形式チェック、所在 IP が 127.x / 192.x で始まるものの除外 等。
2. クエリの検索文字列に自分のキーがマッチすれば、そのキーを CKeyHeader 化してクエリに追加する(`CQuery::mf_CQuery_0030`, `CQuery.cpp` L75、最大約30件まで)。マッチ規則(`CKey::mf_CKey_0040`, `CKey.cpp` L186):
- 通常語: ファイル名への部分文字列一致(大文字小文字を区別しない、複数語は AND)
- `-語`: NOT 条件
- `%` + 16進32文字: ハッシュ完全一致
- `#...`: 投稿者 ID 一致
3. クエリを転送する(§7.3)。

CKeyHeader のメモリ内構造(`CKey.h` の `CKeyHeader`、ワイヤ形式は §7.2):
- 所在アドレス2組 (IP+ポート)。ワイヤ上は **平文 IP**(メモリ内の XOR 難読化は書き出し時に解除される。`mf_CQuery_0030`)
- ファイルサイズ(uint32)、ハッシュ(16)、ファイル名(§5.2 形式 + 長さ1バイト)、ID 文字列×2(11バイト級)、参照カウント系 int32 ×2、time_t、フラグ2バイト

### 5.4 キー収集の能動トリガ

- タイプ10(検索)/タイプ16(BBS)を受けると、空のファイル名のクエリを生成してフラッディングする(`mf_CMainControl_0850` / `0860`)。空ファイル名は全キーにマッチするため、実質「持っているキーを返せ」という収集要求になる。同时に処理できるアクティブクエリは最大10(`mf_CMainControl_1100`)。
- タイプ12/15 は、他ノードから「この検索条件でクエリを起こせ」という要求で、受けたノードが発信元になってクエリを流す。
- タイプ24/27 により、特定ハッシュを相手が持つかどうかだけを 1 往復で確認できる。
- タイプ10 の自発送信(`mf_CMainControl_0830`、v3.2 で確定): 1秒タイマから「自ノードの起動後経過秒 % 30 == 0」のときに呼ばれ、有効・接続中・タイプ3受信済み(`m_field_8D`)・転送リンクでない・BBSポートでない・接続後5秒超の全ホストへ、ペイロード `0x0A` 1バイトだけのフレームを送る。**周期は30秒**(位相はノード起動時刻基準)。BBS 版のタイプ16 は `mf_CMainControl_0840` が10秒周期で送る。
- 受信側(`mf_CMainControl_0780`): タイプ10 は**ペイロード長がちょうど1のときだけ** `mf_CMainControl_0850(ホスト)` を呼ぶ。0850 は相手が上り接続なら `mf_CMainControl_1110`、下り接続なら `mf_CMainControl_1120` を呼び、どちらも空条件のクエリ生成(§6.1)に至る。接続方向の判定は §6.2。

転送規則(`mf_CMainControl_1130`):
- 経路ホスト列が空でなければ、末尾のホストを取り除いてそのノードへ送り返す(応答の戻り経路)。
- そうでなければ、自ノードの (IP, 受付ポート) を経路に積み、経路に含まれないダウン接続へフラッディングする。
- 経路長 > 6、またはキーヘッダ ≥ 30 になるとフラグA(応答済み)を立てて拡散を止める。
- NAT 補正: 転送時、相手が NAT 配下で申告アドレスと観測アドレスが食い違う場合、経路/所在アドレスを観測アドレスに置換する処理がある(`mf_CQuery_0060` L194、`mf_CQuery_0070`)。
- プロトコル世代が古い相手(`CHost` のバージョンフィールド < 10900)へは、特定フラグ値を持つキーヘッダを送らない互換分岐がある(`mf_CQuery_0070`)。

### 6.1 空クエリ(タイプ10応答)の正確なバイト形式(v3.2 で確定)

タイプ10 を受けたノードが自分の検索リンクへ流すクエリは、次の経路で生成・送信される(いずれも `CMainControl.cpp`):

1. `mf_CMainControl_0780`: タイプ10(長さ1) → `mf_CMainControl_0850(ホスト)`。
2. `mf_CMainControl_0850`: 相手が上り接続(`GetflgIsUpConnection()`)なら `mf_CMainControl_1110(ホスト, "", "", m_int_unk41, false)`、下りなら `mf_CMainControl_1120(..., false)`。検索文字列・検索者 ID ともに空文字列。
3. `mf_CMainControl_1110` / `1120`: アクティブなクエリ(フラグ `m_flg_unk04` 立ち)が10未満なら `mf_CMainControl_1130(ホスト, "", "", NULL, 0, 下りフラグ, m_int_unk41, false)` を呼ぶ。
4. `mf_CMainControl_1130`(新規生成パス): 空きスロットに `CQuery::mf_CQuery_0000(検索文字列, 検索者ID, シリアル)` で初期化し、発信元を自ノードに設定(`SetIpaddr(自ノードの ipaddr3)` / `SetPort(m_port_accept_)`)。フラグは 1110 経由で `m_flg_unk03=false`、1120 経由で `m_flg_unk03=true`、いずれも `m_flg_unk01=true`(発信元形式)。1130 自身は送信しない。
5. 送信はメインループの受信処理直後に呼ばれる `mf_CMainControl_1090` が行う: 経路が空のクエリには**自ノード (ipaddr3, m_port_accept_) を経路に積み**、1110 形式(`unk03=false`)は適格な**上り接続すべて**へ、1120 形式(`unk03=true`)は**下り接続のみ**へフラッディングする(宛先はタイプ10 の送り主だけではない)。フラッディング適格条件: 有効・接続中・BBS フラグ一致・(非 BBS クエリでは)相手が Port0 でないこと・BBS ポートでない・接続後5秒超・転送リンクでない・下り接続でない(1110 形式時)。

生成時の付随値:
- シリアル(`m_int_unk2`、§6 表のオフセット5)は 0850 の引数 `m_int_unk41`。このカウンタは BBS クラスタ自動検索(`mf_CMainControl_1070`)と UI 検索(`mf_CMainControl_1080`)でしか増えないため、**検索をしたことのないノードでは常に 0**。
- キー同梱: 発信元形式(`unk01=true`)のクエリには、生成時に**自分のキーバッファのキーだけ**が回転ウィンドウ方式で同梱されうる(中継ノードは発信元形式クエリへキーを追加しない。追加マッチは UI 検索形式 `unk01=false` でのみ起きる)。キーを持たないノードでは同梱 0 件。
- 受信側の扱い: 発信元形式のクエリを受け取ったノードは、同梱ヘッダをキーバッファへ登録したうえでクエリを**無効化する**(転送・キー追加をしない)。つまりタイプ10 応答クエリは宛先ノードで静かに吸収される。キー収集が実るのは、相手が自発タイプ10 に応えて流すクエリや、他ノードの UI 検索クエリが自リンクへフラッディングされてくる経路。

以上より、キーを持たないノードがタイプ10 へ応答する際のワイヤバイトは**固定30バイト**:

| オフセット | サイズ | 値 |
|---|---|---|
| 0 | 1 | 13 |
| 1 | 1 | `m_flg_unk02` = 0 |
| 2 | 1 | `m_flg_unk01` = 1(発信元形式) |
| 3 | 1 | `m_flg_unk03` = 0(1110/上り応答)または 1(1120/下り応答) |
| 4 | 1 | BBS フラグ = 0 |
| 5 | 4 | シリアル int32 = 0(検索をしたことのないノード) |
| 9 | 1 | 検索文字列長 = 0 |
| 10 | 11 | 検索者 ID = 全 0(空文字列の 11 バイト固定欄) |
| 21 | 1 | 経路ホスト数 = 1 |
| 22 | 4+2 | 経路[0] = 自ノード ipaddr3 + `m_port_accept_`(uint16) |
| 28 | 2 | キーヘッダ数 = 0 |

(直列化順序は `CQuery::mf_CQuery_0070`。フレーミングは通常どおり int32 長 + ペイロード。)

### 6.2 リンク保持の規則と自ノード申告(v3.2 で確定)

毎秒タイマから呼ばれる `mf_CMainControl_1140` が全接続を走査し、次の条件で切断する:

- **接続経過 > 20秒 かつ (タイプ3 で申告されたポート == 0 またはタイプ3 未受信)**: 無条件に切断。実地2回目(2026-11-09、v3.1)の「約21秒でタイプ10 が届き約1秒後に EOF」はこの規則で完全に説明できる(タイプ10 の30秒周期とは無関係の偶然の一致)。
- 無通信時間 > 300秒: 切断(受信のたびにリセットされる)。

自ノード申告(`mf_CMainControl_0670`)の要点:
- タイプ3 のポート欄には `m_port_accept_`(ini の `AcceptPort`、未設定時は 1024〜32766 のランダム値)がそのまま書かれる。**Port0 状態でも 0 にはならない**。ポート未開放は別の申告で伝えられる: タイプ2 のバイト[1] = `m_optflag_notConnected__`(ポート開放確認に失敗したノードが立てるオプション)由来。AcceptPort が範囲外 (≤0 や >32767) の場合はランダム値に置き換えられ、同時に `NotConnected=1` が書かれる。
- タイプ3 の IP 欄と、クエリの発信元/経路の IP は、自ノードエントリの `m_ipaddr3` = 起動時に `gethostbyname(gethostname())` で得た**自分の LAN IP が設計値**(実地で相手が 192.168.0.148 を申告していたのはこのため)。

接続方向の判定(`mf_CMainControl_0790`、タイプ3 受信時に実施):
- 相手が Port0(タイプ2 バイト[1] 由来のフラグ)なら無条件に下り接続。
- それ以外は速度比 = 相手の int 化された回線速度 / 自分の速度。> 1.5 なら上り、< 2/3 なら下り、帯域内は現状維持(新規接続の初期値は「下りでない」)。速度はタイプ1 受信時に `(int)` へ切り捨てて保持される。

当クローラの申告値と実クライアントとの差異(意図的なもの):
- IP は 127.0.0.1 を申告(実クライアントなら LAN IP)。観測用の虚偽申告であり、相手の自己接続判定(相手自身の ipaddr3 + 受付ポートとの一致)に触れない範囲で無害と判断。
- 受付ポート欄は 7743 を固定申告(実クライアントなら ini 設定値/ランダム)。**待ち受けは一切しておらず到達可能性はない**。Port0 性は従来どおりタイプ2 バイト[1] = 1 で申告しており、相手側の方向判定(当方を下り扱い)やフラッディング適格判定は実 Port0 ノードと同一になる。
- タイプ10 の周期送信は接続起点の30秒毎(実クライアントはノード起動起点の30秒毎で位相が異なる)。

### 6.3 タイプ31の正体・1140 の全条件・クエリ生成トリガ(v3.3 調査で確定)

**タイプ31(長さ1)は「紹介バッチの終端マーカー」**。紹介ワーク `mf_CMainControl_1000` はタイプ4 を最大31件送った後、ワークの `m_flgkasiraso_5` が立っていればタイプ31 を1バイト送る。このフラグは `CWork::mf_CWork_0130(hostIdx, true)` で生成されたワーク(紹介ワークは常にこの生成経路)に立つ。生成箇所は2系統のみ:(a) `mf_CMainControl_0790`(タイプ3 処理時、速度比が帯域 [1/19.9, 19.9] の外れた相手との「紹介だけ交換」経路)、(b) 後述 1140 のリンク数整理(上限ちょうどで最下位ホストに生成)。同じバイト31 は「リンクを閉じる際の作法」として他の経路でも送られる:受信ソケット異常時(`mf_CMainControl_0360`)、ダウンロード完了後の切断時(`mf_CMainControl_0890` 内)、ワークタイムアウト時(`mf_CMainControl_0800`)、改竄検知時(1140、後述)。受信側ディスパッチャ `mf_CMainControl_0780` にタイプ31 のハンドラは**存在せず、応答は期待されない**(無視してよい)。なお 0780 の末尾には「未処理タイプは切断、ただし 0 と 0x60〜0x63(v66 では 0x61〜0x63)は読み飛ばす」という再構成があり、31 を送る実装が日常的に存在することと矛盾して見える。再構成の取り違えの可能性が残るため、この末尾条件は未確定事項とする(§9)。実地では相手(実クライアント)が紹介バッチ毎に 31 を送り続けた事実のみ確定している。

**`mf_CMainControl_1140`(毎秒)の切断・整理条件の全容**(接続中ホストへの毎秒走査):
- 自己接続判定:相手の申告ポート == 自分の受付ポート かつ 相手 IP が自分の IP と内部的に一致 → 切断。
- **接続経過 > 20秒 かつ (申告ポート == 0 または タイプ3 未受信) → 切断**(§6.2 の規則)。加えて「要注意 Port0」フラグ (`m_flgIsBadPortZero_9`) が立っているか、無通信 > 300秒でも切断される(nodata は受信・送信フラッシュのたびにリセット)。
- **即時切断(接続経過 > 1秒で発火):相手が Port0 かつ 相手の申告速度 >= 自分の速度 かつ 転送リンクでない かつ 相手が BBS ノードでない → 切断**。Port0 リンクは「自分より遅い相手」にしか張れない設計。当クローラの申告速度 100 に対し、速度 50 のノードへのスノーボールが約1.3秒で EOF になったのはこの規則で説明できる(実地3回目)。
- 自分が Port0(`m_optflag_notConnected__`)かつ相手も Port0 → 切断(Port0 同士は検索リンクを張らない)。
- BBS 関係:BBS ノードかつ転送リンクで接続経過 > 120秒 → 切断。BBS 専用モード(`m_optflg_UseBbsOnly_`)では非 BBS の相手を切断(タイプ2 受信時にも即時判定があり、BBS 専用ノードへの通常接続はハンドシェイク直後に切断されうる。実地3回目の速度1000・BBS ノードへの 0.4秒 EOF の最有力候補)。
- 「!'送信(切断そのものではない):相手が非 Port0 かつ タイプ3 受信済み かつ 接続経過 > 30秒 かつ `m_flgUnknown_80` でない → 警告バイト '!' (0x21) を送り `m_flgIsBadPortZero_9` を立てる(次回走査の切断条件に直結)。Port0 相手には送られない。
- 改竄検知時のタイプ31 送信(切断ではない):exe ハッシュ不一致 かつ 接続経過 >= 350秒(= `g_int_unk415` 10 × 35)、メモリ署名不一致 かつ >= 385秒(= 11 × 35)。実地で観測された接続直後からの 31 はこの経路では説明できない(上記の紹介終端が正体)。
- 同一 IP:ポートの重複接続は若い方を切断(検索/BBS/転送の4変種)。
- **リンク数の上限管理(本調査の核心)**:毎秒、接続を数え直し、以下の上限で「最下位」ホストを整理する。ちょうど上限のときは最下位ホストへ紹介ワーク (タイプ4 バッチ + 終端 31) を生成し、上限を超えたら最下位ホストを切断する(1秒に1件ずつ)。警告バイトは送られない(転送リンク整理でのみ ' ' が先行する)。
  - Port0 の下り検索リンク:上限 **3**。下り検索リンク全体:上限 **6**。最下位の判定は `m_int_unk10` 最小。
  - BBS の Port0 下り:上限 6、BBS 下り全体:上限 10。こちらは接続経過が最小(最も若い)ホストが対象。
  - 上り検索リンクが 3 を超えたら毎秒1件切断。上り BBS は 3(クラスタ参加時)または 4 を超えたら最下位を切断。
- `m_int_unk10`(優先度スコア)の正体:`mf_CMainControl_0170` が `CHost::mf_CHost_0220` で計算する**クラスタ語の類似度**(相手と自分のクラスタ語同士で部分一致した語の長さの合計、2文字未満の語は無視)に、ダウンロード完了時に相手へ付与される `m_int_preference2_positive`(+20/回) を加えたもの(上限100)。**クラスタ語が空でダウンロード提供実績のないホストは恒常的に 0 = 最下位**になる。
- この他、タイマーブロックには `mf_CMainControl_0330(false)`(Port0 検索リンクと転送リンクの**一斉切断**)が 600秒(自動切断オプション時)または 3600秒周期で用意されている。
- **「クエリが来ないリンクを切る」規則は 1140 内に存在しない**。無通信の上限は nodata 300秒のみで、紹介・クエリ等の受信でもリセットされる。

**クエリ生成のトリガ(自発フラッディングの有無)**:
- 接続確立そのものではクエリは生成されない(確立時に生成されうるのは紹介ワークのみ)。
- タイプ10 受信 → `mf_CMainControl_0850` → 1110/1120 → `mf_CMainControl_1130` が空クエリを生成し、**自分のキーバッファから速度に応じた件数のキーを同梱**して `mf_CMainControl_1090` が拡散する。タイプ16 は BBS 版の同経路(0860)。
- タイプ13 受信 → `mf_CMainControl_1100` → 1130 が転送用クエリを再構成し、自分のキーの一欠片を追加して再拡散する(経路に自分が含まれていれば打ち止め)。
- タイプ10 の自己生成は `mf_CMainControl_0830` が起動後経過 %30 == 0 のタイミングで、確立済み(タイプ3 受信済み・接続経過 > 5秒・非転送)の全リンクへ送信する。
- 実地3回目で相手からキー438件のクエリが3回届いたのは、当方がタイプ10 を送っていない以上、相手が他リンクから受けた拡散クエリを転送したものとみるのが整合的である(同一内容の複数回線到着→複数回転送)。

**実地3回目(2026-11-09、v3.2)のエントリ切断(+24.2秒)についての結論**:
相手は接続+6秒から約1.1秒間隔で「紹介31件 + 終端31」を16回送り、最後のバッチの約1秒後に EOF した。これは 1140 の上限管理そのものの挙動である:当方のリンクが「上限ちょうど」で最下位に選ばれ続けて紹介ワークを受け取り、上限超過の瞬間に最下位として切断された。当方はクラスタ語が空・ダウンロード実績なしのため `m_int_unk10` が恒常的に最小であり、相手側の事情(他リンクの増減)だけで生死が決まる。**これは実 Port0 ノードでも同じ扱いであり、クライアント側の不具合ではない**。相手のカウンタが Port0 下り (3→4) と下り全体 (6→7) のどちらで超過したかは外部から観測できない。次点の候補は 0330 の一斉切断(600/3600秒周期との偶然の一致が必要で、紹介の波は説明できない)。

## 7. 初期ノード文字列のデコード手順

コーデックは `CKey::mf_CKey_0270(テンプレート, 出力)`(`CKey.cpp` L1093)。エンコード側の使用例が `IpConvUnit.cpp` の `Button1Click`(L33): 平文 `"IP:ポート"` を `CKey::mf_CKey_0070`(L395、モード値 `m_int_unk203=1` で平文コピー)でセットし、`mf_CKey_0270("opiewf6ascxlv", out)` で `@` 文字列化する。

### 7.1 形式
```
"@" + hex(チェックサム1バイト) + hex(RC4暗号文)
```
16進は小文字 `%02x` 形式。

### 7.2 デコード手順(検証可能)
入力が `@` で始まる場合:
1. `@` を除いた残りを 2 文字ずつ 16 進としてデコードし、バイト列 B[0..n) を得る。
2. B[0] がチェックサム。RC4 鍵 = テンプレート `"opiewf6ascxlv"` の **先頭1バイトを B[0] に置換した文字列**(すなわち `[B[0]] + "piewf6ascxlv"`、14バイト)。
3. B[1..n) をその RC4 で復号する。
4. 検証: 復号バイト列の合計 mod 256 == B[0]、かつ全バイト ≥ 0x20。成功すれば復号文字列が平文 `"ホスト名:ポート"`。失敗時は出力が `"@"` になり、その行は無効として捨てられる。

エンコードはその逆: チェックサム = 平文バイト合計 mod 256、鍵 = `[チェックサム] + "piewf6ascxlv"` で暗号化し、`@` + 16進で出力する。

### 7.3 具体例について
ソース内・リポジトリ内に、検証に使える実物のノード文字列サンプルは**含まれていない**(Noderef.txt の実ファイルも同梱されていない)。テストベクタは §7.2 の手順で自作し、相互にエンコード/デコードが一致することで検証するしかない → (実在ノード文字列での検証はフェーズ2-2以降)。

## 8. バージョン差

`src/66`、`src/70`、`src/71` の比較から:
| | b6.6 | b7.0 | b7.1(本仕様) |
|---|---|---|---|
| ハローのバージョン int32 | 12660 | 12700 | 12710 |
| 送信する識別文字列 | `"Winny Ver2.0b1 "` | `"Winny Ver2.0b1 "` | 同左 |
| 相手の受け入れ条件 | 文字列 `"Winny Ver2.0b1"` の 14 バイト一致 かつ バージョン ∈ [12647, 12800) | 文字列 `"Winny Ver2.0"` の 12 バイト一致 かつ [12660, 12900) ∪ [20000, 21000) | b7.0 と同じ |


- バージョン範囲 **[20000, 21000)** が受け入れ対象に含まれていることから、現行ネットワークにはバージョン番号 20000 番台を名乗る別系統のクライアント(派生/互換実装の可能性)が存在しうる。本ソースからはその正体は分からない。
- クエリ直列化にある「相手バージョンフィールド < 10900」分岐は、さらに古い世代のプロトコルとの互換処理とみられるが、そのフィールドの由来(どのパケットで運ばれるか)は追跡しきれていない。
- 2026 年現在の実ネットワークの主流バージョンは、このソースだけでは**判断できない**。観測実装は、受け入れ範囲内ならバージョンを問わず接続できる設計(送信バージョンは 12710)にしておくのが安全。

## 9. 実装上の未確定事項リスト

ソース精読だけでは確定できなかった事項。優先度順:

1. **ブートストラップ手段(最重要)**: 初期ノード文字列/Noderef.txt の入手経路はソースに含まれない。2026 年現在、実ネットワークに入るための初期ノードをどこから得るかはソース外の問題(実在の配布経路の調査が必要)。
2. **実トラフィックとの一致**: 本ソースは再構成であり、特に以下の点は実バイナリ/実パケットでの検証が必要。
- ハロー前後の RC4 再鍵タイミングの厳密な境界(どのバイトから新鍵になるか)
- シード内 0x00 時の実効鍵長の扱い(両実装が本当に同じ規則か)
- タイプ3 のオフセット 8 以降(DDNS 名とクラスタワードの並び)の解釈
3. **テストベクタなし**: ノード文字列・キャッシュファイル等の実サンプルがリポジトリに無く、コーデック実装の正しさを実物で検証できない。
4. **バージョン 20000 番台クライアントの正体**と、現行ネットワークの主流(§8)。
5. **`mf_CMainControl_0770`**(相手バージョン > 自バージョン時の処理)未精読。
6. **タイプ17(`mf_CMainControl_1390`)、タイプ21(`mf_CMainControl_0920`)、タイプ31** の意味未精読/未確定。観測には不要と判断したが、受信時に想定外の切断要因にならないかは未検証。
7. **タイプ11 の第2引数以降と `mf_CMainControl_1520`(所有判定)の詳細**未精読(タイプ24/27 の応答値の厳密な意味付けに影響)。
8. **ファイルハッシュの算出方法**: 16バイト値が MD5 である蓋然性は高いが、「ファイル内容の何をどうハッシュするか」はキー生成経路(`mf_CKey_0110` 等)を精読しないと確定できない。観測(受信して記録するだけ)には不問。
9. **回線速度の単位**(タイプ1 の float、タイプ4 の int32): 単位・スケールの定義を特定できていない(コード内の `/40` 等の使用から KB/s 級と推測されるに留まる)。
10. **`mf_CMainControl_0790` の方向決定条件の全容**と、クラスタワード不一致時の扱い(BBS 以外で不一致だと切断されるのか、方向だけ変わるのか)。観測ノードが「どのクラスタに参加すべきか」に直結するため、フェーズ2-2 の前に追加精読が望ましい。
11. **キー種別 KEYTYPE00–03 の厳密な意味**と、CKeyHeader フラグ2バイト・値1(`m_int_unk10`)の意味論。
12. **クエリ付随 int32(`m_int_unk2`)** の意味(TTL か、ID か、優先度か)。
13. ポート0ノード(着信不可)との接続維持方法の詳細(タイプ22/23 のリレー手順は概形のみ確認)。観測ノード側が着信可能ポートを持つ前提なら当面不要。

## 10. 観測クローラの最小実装手順(まとめ)

1. Noderef 形式の行(平文または `@` 形式)を §7 の手順で解釈し、(ホスト, ポート)を得る。
2. TCP 接続し、自分のシード4バイトを生成。最初の送信で「ランダム2バイト + シード4バイト」を平文前置し、シード文字列鍵の RC4 で §2.2 の列(マーカー、ハロー、タイプ1、タイプ2、タイプ3)を送る。
3. 受信は相手の先頭6バイトから相手シードを取り込んで RC4 を開始し、フレーム(§3)を順次復号。相手ハローを検証した時点で受信 RC4 を §2.4 の鍵で再初期化する。
4. タイプ4 を収集してノードバッファを育て、タイプ3/4 の情報から新規ノードへ接続を広げる(スノーボール)。
5. キー情報は、接続先から流れてくるタイプ13 クエリ内の CKeyHeader を受動的に記録する。能動収集する場合はタイプ10 を送って空クエリのフラッディングを促す。ファイル名は §5.2 の手順で復号する。
6. コンテンツ本体の転送(タイプ11/21 等)には一切関与しない。
